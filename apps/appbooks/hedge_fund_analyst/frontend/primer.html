PRIMER · ORACLE DEEP DATA SECURITY

The database decideswho sees which rows, columns and cells, for every statement, whoever wrote the SQL.

An agent can write any SQL. A prompt can say anything. Deep Data Security (DDS) moves the access decision out of the prompt and the application and into Oracle AI Database, where it applies to the end user behind the request. This page teaches it from the objects the Hedge Fund Analyst demo actually created, then lets you prove it against the live database.

Verified on this database = run here on Oracle AI Database 26ai Free 23.26.2 From Oracle docs = documented, not exercised in this demo

01 · THE IDEA

One rule, enforced underneath the agent

Without DDS, an agent's database account usually sees everything, and the application (or the prompt) is trusted to filter. With DDS, the database knows the end user and applies that user's data grants to every statement, including model-written SQL, so the same query returns different, correctly entitled results for different people.

1 · statementAgent runs SQLSELECT … FROM HF_POSITIONS
→
2 · whoEnd userhf_credit
→
3 · which rolesData roleHF_CREDIT_ROLE
→
4 · which rows / columnsData grantWHERE desk = 'Credit'
→
5 · result + auditOnly entitled rowsaudited as hf_credit

Without DDS

  • Filters live in app code and prompts (WHERE desk = :desk).
  • A prompt injection or a buggy tool path can drop the filter.
  • Audit shows the agent's account, not the person.

With DDS

  • Filters live in the database as data grants.
  • Model-written SQL, OR 1=1, and “show both desks” still return only entitled rows.
  • Unified Auditing records the end user.

02 · BUILDING BLOCKS

Five objects you need to know

End user

The person (or caller) the database authorizes. Created in the database or mapped from an identity provider (Microsoft Entra ID, OCI IAM).

CREATE END USER "hf_credit" IDENTIFIED BY "…";   -- direct logon (this demo)
CREATE END USER emma;                            -- no password: identity asserted by the application

Verified both forms accepted on 23.26.2.

Data role

A role that carries data grants. Granted to end users; it can also carry ordinary roles (for example, a role with CREATE SESSION, without which the end user cannot log in).

CREATE DATA ROLE HF_CREDIT_ROLE;
GRANT HF_CONNECT TO HF_CREDIT_ROLE;        -- HF_CONNECT has CREATE SESSION
GRANT DATA ROLE HF_CREDIT_ROLE TO "hf_credit";

Verified a data role without a login role gave ORA-01045.

Data grant

The rule: which operation, on which object, which rows (a WHERE predicate) and optionally which columns, for which data role.

CREATE DATA GRANT HF_OWNER.HF_POSITIONS_CREDIT
  AS SELECT ON HF_OWNER.HF_POSITIONS
  WHERE desk = 'Credit' TO HF_CREDIT_ROLE;

-- column-limited (hide margin), from the Oracle example
CREATE OR REPLACE DATA GRANT owner.dg_desk_a
  AS SELECT (id, desk, counterparty, notional)
  ON owner.positions WHERE desk = 'A' TO desk_a_role;
SET USE DATA GRANTS ONLY ON owner.positions ENABLED;

Verified row grants in the demo; column-limited grant and SET USE DATA GRANTS ONLY accepted on 23.26.2 (whether a hidden column errors or returns NULL was not yet tested).

End-user security context

For agents that connect with their own account: a payload attached per request carrying the end user's identity, a database-access token from an identity provider, optional extra data roles and context attributes. Oracle validates it, applies it for that request, and swaps or clears it when the connection is reused or released.

ctx = oracledb.create_end_user_security_context(
    end_user_identity=user_token,          # or local end-user name + key
    database_access_token=db_token,         # IAM on-behalf-of or client credentials
    data_roles=["hcm_role"], attributes={...})
connection.set_end_user_security_context(ctx)
…  # run the agent's SQL
connection.clear_end_user_security_context()

From Oracle docs python-oracledb 4.0+ Thin mode; the agent account needs CREATE SESSION and CREATE END USER SECURITY CONTEXT (privilege grant verified).

Application identity

The agent or application as a first-class principal, mapped to its identity-provider client. It can be granted data roles (including disabled ones it may enable for a task); from 23.26.3 it can also be the logon principal that attaches end-user contexts.

CREATE OR REPLACE APPLICATION IDENTITY hcm_app
  MAPPED TO 'AZURE_CLIENT_ID=…';
CREATE OR REPLACE DATA ROLE summarize_sales_role DISABLED;
GRANT DATA ROLE summarize_sales_role TO hcm_app;

From Oracle docs not used in this demo.

Reading identity in SQL

Predicates, views and audit can read who the end user is. This demo uses both forms.

SELECT ORA_END_USER_CONTEXT.username,
       SYS_CONTEXT('USERENV','AUTHENTICATED_IDENTITY')
FROM dual;   -- hf_credit, hf_credit

Verified the identity survives definer-rights execution, which is why the graph views use it.

What the Hedge Fund Analyst actually created

Identities and roles

End users"hf_credit", "hf_markets" (password, direct logon)
Data rolesHF_CREDIT_ROLE, HF_MARKETS_ROLE, each with HF_CONNECT (CREATE SESSION)
Desk-scoped grantsHF_DESKS, HF_PORTFOLIOS, HF_POSITIONS, HF_COLLATERAL, HF_NOTES, HF_CHUNKS (research vectors), HF_GOLDEN: WHERE desk = '<desk>'

The setup loop (scripts/bootstrap.py)

CREATE ROLE HF_CONNECT;  GRANT CREATE SESSION TO HF_CONNECT;
-- for each desk in (Credit, Markets):
CREATE DATA ROLE HF_<DESK>_ROLE;
CREATE END USER "hf_<desk>" IDENTIFIED BY "…";
GRANT HF_CONNECT TO HF_<DESK>_ROLE;
GRANT DATA ROLE HF_<DESK>_ROLE TO "hf_<desk>";
-- desk-scoped table
CREATE DATA GRANT HF_OWNER.HF_POSITIONS_<DESK>
  AS SELECT ON HF_OWNER.HF_POSITIONS
  WHERE desk = '<Desk>' TO HF_<DESK>_ROLE;
-- shared table
CREATE DATA GRANT HF_OWNER.HF_ENTITIES_<DESK>
  AS SELECT ON HF_OWNER.HF_ENTITIES TO HF_<DESK>_ROLE;

The app never adds a desk filter. Both the plane and the naive agent connect as the selected end user, so even the naive agent's model-written SQL is entitled.

→

Grants of that user
  • Two tokens: the end user's identity and a database-access token (on-behalf-of or client credentials) from Entra ID or OCI IAM.

06 · LESSONS FROM BUILDING THIS

What we hit, so you don't have to

Definer-rights objects can bypass grants

SQL property graphs run with the owner's rights. A graph over base tables showed both desks to each analyst. Fix: desk vertices come from views filtered on SYS_CONTEXT('USERENV','AUTHENTICATED_IDENTITY'). Verified

Revalidation restored a stale, leaky graph

After CREATE OR REPLACE PROPERTY GRAPH, invalidating the graph and revalidating it brought back the old base-table definition. Fix: DROP + CREATE, a fail-closed setup check, and a live isolation check in the status row. Verified

True Cache cannot serve DDS end users here

An end-user logon to the read-only True Cache instance fails with ORA-16000. Entitled reads stay on the primary; True Cache serves only identities that hold no other desk's data. Verified

Data roles need a login role

Granting a data role is not enough to connect. Grant a role holding CREATE SESSION to the data role (the demo's HF_CONNECT). Verified

Remove app-side filters, then test

Keep WHERE desk = … out of tool code and prompts, otherwise you are testing the app, not the database. The live checks above use no filter, OR 1=1, and an explicit request for both desks.

Audit tells you who, if you tag the turn

Unified Audit records the end user (END_USER_NAME). Setting a request ID as the session's client identifier lets each agent turn find its own records.
